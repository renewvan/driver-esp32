# Research 02: ESPHome ways to give N boards of one firmware distinct identity

Ticket: `.wayfinder/tickets/02-esphome-per-board-identity.md` (map: `.wayfinder/map.md`).
Research only; nothing here is implemented. Sources are primary ESPHome docs; "Fit" notes read this repo's
`packages/base.yaml`, `firmware/*.yaml` and `scripts/flash.sh`. Claims marked UNVERIFIED were not stated by the docs.

## Findings from the ESPHome docs

1. **Node name** (https://esphome.io/components/esphome/). `name` is required, "should always be unique in your ESPHome
   network", lowercase letters/digits/hyphens only. `friendly_name` is separate (frontend/Home Assistant label).
   `name_add_mac_suffix: true` appends `-aabbcc` (last 3 MAC bytes) so one binary can serve many boards, but the docs warn
   end users then need an individual YAML to OTA later. The docs state a length limit (24 by default; the page text on the
   31-char case is ambiguous), and the current names (`renewvan-esp32-16x-relay`) are already 24 chars: UNVERIFIED how
   much room a suffix leaves.
2. **Substitutions + CLI** (https://esphome.io/components/substitutions/). `substitutions:` defines `${key}`; the global `-s KEY VALUE`
   switch overrides, and "Command line substitutions take precedence over those in your configuration file", so one
   template can serve many devices (`esphome -s name my_device01 config example.yaml`). Substitutions work in `!include`
   filenames, `vars` and `condition`.
3. **CLI** (https://esphome.io/guides/cli/). `-s/--substitution KEY VALUE` is a global option placed BEFORE the command and
   repeatable. `run`/`upload` take `--device` (serial port or IP; an IP means OTA). `--device OTA` resolves the address via
   MQTT, DNS or mDNS (order not given). `--device` may repeat as ordered fallbacks. `esphome config` validates and prints
   the resolved config (`--show-secrets`, `--no-defaults`), so `esphome -s device_name x config firmware/y.yaml` previews an
   override.
4. **Packages** (https://esphome.io/components/packages/). `!include` accepts variables (`vars`) and a package can declare
   `defaults:` for ones not passed, so one package can be instantiated several times with different values. Merge: dicts
   by key, component lists by ID, other lists concatenated, scalars replaced by the later value. "Substitutions in your
   main configuration will override substitutions with the same name in a package." Remote packages cannot use `!secret`.
5. **WiFi addressing** (https://esphome.io/components/wifi/). `use_address` overrides the address used to reach the node;
   `manual_ip` makes OTA target that IP automatically; `domain` (default `.local`) means uploads go to
   `<HOSTNAME>.local`. So per-board OTA is by mDNS hostname (= node name) by default, or by IP via `manual_ip`/`use_address`
   or `--device <ip>`.
6. **OTA component** (https://esphome.io/components/ota/esphome/). `password` per `ota:` platform (marked "not recommended for new
   devices, use encryption"); port 3232 on ESP32. The page does not say how the upload address is chosen (see 5).
7. **MQTT identity** (https://esphome.io/components/mqtt/). Topics are prefixed by node name unless `topic_prefix` is set;
   `topic_prefix: null` disables every topic not explicitly configured. `discovery` (default true) and `discover_ip`
   (default true; answers `esphome/discover` and `esphome/ping/<APP_NAME>`, used by the dashboard and the CLI for IP
   lookup) are separate switches. `client_id` is "generated by using your node name and adding the MAC address", so it is
   unique per board even if names collided. Birth/will default to retained `<prefix>/status` `online`/`offline`; both are
   plain `topic`/`payload`/`retain` mappings that may be overridden, so they can contain substitutions. `shutdown_message`
   is sent on a clean disconnect instead of the will. The docs tie empty birth/will topics to availability reporting being
   disabled; they do not describe empty-birth as a general off switch beyond that.

## Options for build-time identity

- **A. CLI substitutions per instance (recommended base).** Keep one YAML per variant; `flash.sh <variant> --board <id>` adds
  `-s device_name`, `-s friendly_name`, `-s fallback_ap_ssid`, `-s board_id`. Zero YAML duplication; docs-guaranteed
  precedence. Requires a defined place for per-instance values (UNDECIDED, belongs to a later ticket).
- **B. `name_add_mac_suffix`.** One binary for all boards of a kind, unique names for free, and a self-describing board. Cost:
  node name no longer predictable, so OTA by name needs discovery or a lookup table, and the docs call this out as unfriendly
  to later OTA by end users.
- **C. Wrapper YAML per instance using `packages` with `vars`.** `firmware/<board>.yaml` includes the variant file with vars.
  Documented and explicit, but N files per van and the CI guard "manifest == variant" must learn instances.
- **D. Runtime-only identity.** Same binary, identity read from MAC (`board_serial`) and announced over MQTT, hub assigns
  names. Matches the map's leaning (self-describing). Does not by itself fix will/health sharing; the will topic is fixed
  at build time, so a MAC-derived topic needs a lambda-built topic (UNVERIFIED that `will_message.topic` accepts a
  templatable value; the docs read show a literal string only), otherwise build-time `-s board_id` is required.
